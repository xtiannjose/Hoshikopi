## Ordering core: Cart, pricing, placement, Capacity, Pickup Windows, Order Status

The core ordering logic is mostly sound. The server prices every Line again inside the placeOrder transaction and compares the result to the total the Customer saw, so client totals are never charged. Option Group min/max, Sold Out, Hidden, Seasonal and Promo checks all run in priceChoices. Lines snapshot names, Options and prices, and the reward-split Lines sum correctly. A grep found no Order Status write outside transition(). Capacity is checked under a FOR UPDATE row lock, and cancelling or expiring an Order gives back its window counts and reserved Stars in the same transaction (I saw the window return to 0/0 after cancelling my test Orders). Money stays in integer centavos throughout.

Testing against the live app found two real bugs in core flows:
- **Double submit:** replaying one checkout submit twice at the same time created two Orders (K-003 and K-004) from one Cart. Nothing on the server makes placement idempotent.
- **Sign-in crash:** signing in with a Guest Cart and landing on /cart crashed the page 3 times out of 3, with "This page couldn't load" (Prisma errors P2002 on carts_member_id_key and P2025 on cart.delete). The header Cart button and the page each run mergeGuestCart at the same moment.

Other findings, confirmed in the app or with tests and logs:
- A 13 to 15 drink Order, which ORD-12 allows, can never be placed under the default 12-drink Capacity. Checkout says "No Pickup Times are left today".
- Six concurrent adds to the Cart produced quantity 2 (lost updates).
- Running Promise.all inside the placement transaction triggers pg's deprecation warning; that pattern will be removed in pg@9.
- The As Soon As Possible label reads "Ready in about 5 min, around 2:30 PM" at 2:14 PM.

From code review:
- A late paid webhook after an Order expires or is cancelled is silently ignored, and there is no in-app refund path.
- If the payment page fails to start, the Cart is still emptied and Stars and Capacity stay held.
- Stale Pay at Pickup Orders are never closed.
- ORD-02 promises Option editing in the Cart; it is missing.
- There are several doc and test gaps.

#### ORD-01 Double submit at checkout places two Orders from one Cart (no idempotency)

- **high** bug, effort S, confidence 95%
- **Where:** `src/modules/ordering/internal/place.ts:189`, `src/modules/ordering/internal/place.ts:302`, `src/app/(site)/checkout/actions.ts:67`, `src/app/(site)/checkout/checkout-form.tsx:209`
- **Evidence:** Steps: as a Guest, added 1 Hoshi Latte, filled checkout (Pay at Pickup, 8:45 PM), captured the server action POST and replayed it twice at the same time with the same cookies (scratchpad/audit/ordering/double-submit.mjs). Both responses were 200 with different x-action-redirect values (/orders/5da39872... and /orders/4edb824c...). DB: two Orders, K-003 and K-004, each 18500 centavos with 1 x Hoshi Latte, and pickup_window_usage 20:45 drinks=2. Cause: getCart(input.owner, tx) at place.ts:189 reads the Cart Lines without locking the Cart, and clearCart at :302 deletes nothing in the second transaction. The only protection is the client-side `disabled={pending}` and React's action queue.
- **Impact:** A double tap before hydration, a network retry, two tabs or a replayed request creates duplicate Orders. Each one takes Capacity and an Order Code, appears on the Bar Screen (Pay at Pickup, so it is made and wasted) or opens a second online checkout. The Customer cannot see the duplicate.
- **Fix:** Serialize placement per Cart. At the start of the transaction, run `SELECT id FROM carts WHERE <owner> FOR UPDATE` and then read the Lines, so the second transaction finds an empty Cart. Better: put a one-time checkout nonce in the form, store it on orders with a UNIQUE constraint, and on conflict redirect to the existing Order. Add a db test that runs two placeOrder calls on the same Cart at once.

#### ORD-02 Signing in with a Guest Cart crashes the first page (concurrent mergeGuestCart: P2002 / P2025)

- **high** bug, effort S, confidence 95%
- **Where:** `src/modules/cart/internal/session.ts:23`, `src/modules/cart/internal/cart.ts:192`, `src/modules/cart/internal/cart.ts:202`, `src/modules/cart/internal/cart.ts:230`, `src/components/shell/cart-button.tsx:23`, `src/app/(site)/cart/page.tsx:60`
- **Evidence:** Steps: as a Guest, added 3 items, signed in by email link with next=/cart (scratchpad/audit/ordering/merge.mjs). It failed 3 times out of 3: the page showed "This page couldn't load. A server error occurred. Reload to try again." (ERROR 3992331819, 3429499469). server.log shows `Invalid prisma.cart.upsert() invocation: Unique constraint failed on the constraint: carts_member_id_key` (P2002) for a new Member, and `Invalid prisma.cart.delete() ... No record was found for a delete` (P2025) when the Member already had a Cart. Cause: currentCartOwner() is not request-deduplicated, and the header CartButton and the Cart/Checkout page each call it in the same render. That starts two mergeGuestCart transactions at once. Both find the Guest Cart and both upsert the Member Cart; one deletes the Guest Cart, and the other's `tx.cart.delete` throws. The data ended correct (the winning transaction committed).
- **Impact:** Every Guest who builds a Cart and then signs in (the path ORD-05 encourages) lands on an error page. Checkout is the landing page for the sign-in-before-ordering flow. Every later render also runs a merge transaction while the hk_cart cookie remains (it is never cleared).
- **Fix:** Wrap currentCartOwner in React `cache()` so it runs once per request. Make the merge safe under concurrency: lock the Guest Cart row first (`SELECT ... FOR UPDATE`, return if gone), upsert the Member Cart with INSERT ... ON CONFLICT (or catch P2002), and use deleteMany instead of delete. Better still, run the merge once from the sign-in callback, or in a Server Action that also deletes the hk_cart cookie. Add a db test that calls mergeGuestCart twice at once.

#### ORD-03 Late paid webhook after Expire/Cancel is silently ignored: Customer charged, no Order, no log, no in-app refund

- **high** bug, effort M, confidence 80%
- **Where:** `src/modules/payments/internal/payments.ts:92`, `src/modules/payments/internal/payments.ts:128`, `src/modules/ordering/internal/webhook.ts:46`, `src/modules/ordering/internal/refund.ts:27`, `src/modules/ordering/internal/bar.ts:26`, `tests/db/payments.test.ts:185`
- **Evidence:** closeCheckout sets the Payment to `expired` in the DB *before* calling `expireCheckout` at the provider, and only logs if the provider call fails (payments.ts:128-140). recordPaymentEvent only looks for a Payment with `status: "pending"` and otherwise returns `{ kind: "ignored" }` (payments.ts:92-99), with no log. The test 'ignores a payment webhook that comes after expiry' expects `ignored`. The comment in webhook.ts:46-53 promises "a payment that lands after its Order Expired is logged for a Manager to refund by hand", but that branch is reached only when the Payment is still pending. refundOrder accepts only `picked_up`, or `cancelled` with paidAt set (refund.ts:27-30), so an expired Order cannot be refunded in the app. The same applies to a Customer or Manager cancel of an unpaid online Order while the Customer is still on the provider page.
- **Impact:** Payments are judged as production code. A payment that completes in the race window, or after a failed provider expire call (network error), takes the Customer's money but leaves no Order and no record (providerPaymentId is never stored). Nobody is alerted and there is no refund path. This breaks money integrity and docs/04 invariant 3.
- **Fix:** On a paid event for a non-pending Payment, or for an Order that is no longer Placed, store providerPaymentId and set the Payment to a new `paid_late` status (or keep `paid`). Log at error level and refund automatically through the provider, or list it on /manage/orders with a Refund button. Call expireCheckout before marking the Payment expired, and keep it pending if the provider call fails. Add tests for both paths.

#### ORD-04 Orders of 13-15 drinks can never be placed; checkout wrongly says no Pickup Times are left

- **medium** bug, effort S, confidence 95%
- **Where:** `src/modules/ordering/internal/rules.ts:2`, `src/modules/cafe/internal/ordering-day.ts:66`, `src/app/(site)/checkout/page.tsx:131`, `src/app/(site)/checkout/actions.ts:58`
- **Evidence:** MAX_DRINKS_PER_ORDER = 15 (ORD-12), but ADR 0007 seeds 12 drinks per window, and pickupWindows offers a window only when `drinksLeft >= options.need.drinks`. Live at 2:14 PM with 26 empty windows: a Guest Cart of 13 x Hoshi Latte at /checkout shows "No Pickup Times are left today. Walk in and order at the counter." (screenshot scratchpad/audit/ordering/checkout-13.png). The Cart page shows a normal "Check out" button. The same happens for more than 8 food Lines (food Capacity 8).
- **Impact:** A rule the PRD promises (up to 15 drinks) does not work under default settings, and the message is false: the day is wide open. Large-order Customers are sent to the counter instead of to the Inquiry form.
- **Fix:** Cap an Order at min(MAX_DRINKS_PER_ORDER, the day's drinks Capacity) and food Lines likewise, both in the Cart page and in placeOrder, with the ORD-12 Inquiry message. Or spread a big Order across back-to-back windows. Give checkout a separate message when the Order is bigger than any window. Add a test with need > Capacity.

#### ORD-05 Payment page failure (and failed payment) leaves a Placed Order, an emptied Cart and held Stars/Capacity, with no retry

- **medium** bug, effort M, confidence 85%
- **Where:** `src/modules/ordering/internal/place.ts:302`, `src/modules/ordering/internal/place.ts:320`, `src/app/(site)/checkout/actions.ts:54`, `src/app/(site)/orders/[id]/page.tsx:119`, `docs/03-ARCHITECTURE.md:89`
- **Evidence:** clearCart runs inside the committed placement transaction (place.ts:302). startPayment runs after commit (place.ts:320-333). If it throws, the action returns only `payment_start_failed`, the message is "We couldn't open the payment page. Try again, or choose Pay at Pickup.", and the Order id and access token are dropped. Window counts and any reserved 9 Stars stay held until expireUnpaid runs 15 minutes later, so retrying with the Reward gets "You need 9 Stars". After a failed payment, the status page says "place it again" (page.tsx:119-124), but the Cart is already empty and recordPaymentEvent ignores later events for a `failed` Payment. docs/03 section 6 step 6 says the checkout session is created before commit.
- **Impact:** The 'Try again' path cannot work: the Customer has to rebuild the Cart, may lose their Reward for 15 minutes, and a Guest has an orphan Order they cannot see. This error-path code path is also untested (no test mentions payment_start_failed).
- **Fix:** Keep the Cart until the Order is Paid (clear it in the paid transition or on the status page), or offer a 'Pay again' button on the Order page that opens a new checkout for the same Order. On payment_start_failed, cancel the Order right away (releasing the window and Stars) or redirect to its status page with a retry button. Align the docs/03 section 6 text.

#### ORD-06 ASAP takes the window from an unlocked read and is refused 'window_full' instead of moving to the next window

- **medium** bug, effort S, confidence 85%
- **Where:** `src/modules/ordering/internal/place.ts:229`, `src/modules/ordering/internal/place.ts:253`, `src/app/(site)/checkout/actions.ts:60`
- **Evidence:** ASAP sets `windowStart = offered[0].start` from offeredWindows (an unlocked read, place.ts:229-231). If another Order fills that window first, the lock check returns `{ reason: "window_full", nextWindow }`, and the Customer sees "That Pickup Time just filled up. The next one is X." for a time they never chose.
- **Impact:** In a rush, which is exactly when Capacity matters, ASAP Customers get refusals and must resubmit, and each try counts against the 10-per-15-minute checkout limit.
- **Fix:** For pickup.kind === 'asap', try the offered windows in order under the lock (lock, check, and if full move to the next) until one fits, and return no_window only when none do.

#### ORD-07 ORD-02 'edit Options' in the Cart is not implemented

- **medium** gap, effort M, confidence 75%
- **Where:** `src/app/(site)/cart/page.tsx:79`, `src/app/(site)/cart/actions.ts:1`, `docs/01-PRD.md:99`, `docs/07-ROADMAP.md:88`
- **Evidence:** PRD ORD-02 (an M requirement): "The Cart shows Lines, Options, Line totals and the Order total; edit quantity and Options; remove". The Cart page offers only One less, One more and Remove per Line. The name links to /menu/item/<slug>, which adds a *new* Line. There is no action or cart-module function that changes a Line's optionIds (cart/actions.ts has only setQuantityAction and removeLineAction).
- **Impact:** Changing milk or size means removing the Line and building it again. It is also the only way to fix a Line flagged 'invalid_options' or 'option_sold_out'.
- **Fix:** Add 'Change' on each Line that opens the item page with that Line's Options preselected (for example ?line=<id>), and an updateLineOptions(owner, lineId, optionIds) that re-prices and merges by choiceKey. Or record in the PRD and roadmap that MVP editing covers quantity only.

#### ORD-08 Missing tests for the races and refusal paths found here

- **medium** test-gap, effort M, confidence 90%
- **Where:** `tests/db/place-order.test.ts`, `tests/db/cart.test.ts:128`, `tests/db/payments.test.ts:185`
- **Evidence:** grep shows no test for `payment_start_failed`, `paid_late`, `no_window` or `reward_unavailable`. No test places the same Cart twice at once (only two different Carts racing for the last room, place-order.test.ts:240). mergeGuestCart has only a sequential test. #### ORD-09 Order ahead before opening and for tomorrow (ORD-03 V1)

- **medium** feature, effort L, confidence 60%
- **Where:** `src/modules/cafe/internal/ordering-day.ts:94`, `docs/01-PRD.md:100`
- **Evidence:** orderingState refuses with `before_opening` until 7:00, and pickupWindows covers only today. PRD ORD-03 lists "Ordering for tomorrow is V1", but no Phase 6 batch built it. Commuter-focused order-ahead apps commonly let customers schedule the first pickup of the morning the night before.
- **Impact:** The 7:00 to 8:00 commuter rush, the strongest order-ahead use case, cannot be pre-ordered.
- **Fix:** Allow Scheduled Pickup for the next open day from the evening before: build windows from getOrderingDay for that day, store service_day for the pickup day, and keep Capacity and Order Code per pickup day. Online payment only for those Orders (no Pay at Pickup no-shows).

#### ORD-10 Concurrent add-to-cart loses quantity (read-then-write upsert)

- **low** bug, effort S, confidence 90%
- **Where:** `src/modules/cart/internal/cart.ts:86`, `src/modules/cart/internal/cart.ts:89`, `src/modules/cart/internal/cart.ts:91`
- **Evidence:** Replayed the Hoshi Latte add-to-cart action 3 times at once, then 3 more times (scratchpad/audit/ordering/add-race.mjs). All 6 answered `"status":"added"`, but the Cart shows `Hoshi Latte ... 2`. addLine reads `existing.quantity`, computes `quantity` in JavaScript and upserts that absolute value, so concurrent writers overwrite each other. The MAX_LINE_QUANTITY check has the same race; the DB CHECK (1 to 20) still holds.
- **Impact:** Customers who tap Add several times quickly (or use Pairing add plus the main button) see confirmations that do not match the Cart. No money impact, because checkout re-prices.
- **Fix:** Use one statement: `INSERT ... ON CONFLICT (cart_id, choice_key) DO UPDATE SET quantity = cart_lines.quantity + EXCLUDED.quantity WHERE cart_lines.quantity + EXCLUDED.quantity <= 20 RETURNING quantity`. If no row comes back, the result is too_many.

#### ORD-11 Parallel queries inside the placement transaction (Promise.all on tx) trigger pg's deprecation; breaks on pg@9

- **low** inefficiency, effort S, confidence 90%
- **Where:** `src/modules/cafe/internal/ordering-day-db.ts:17`, `src/modules/ordering/internal/place.ts:180`
- **Evidence:** getOrderingDay runs `Promise.all([specialHours, openingHours, capacityRule, cafeSettings])` on the client it is given, and placeOrder passes its interactive `tx`. A read-only tsx run with --trace-deprecation (scratchpad/audit/ordering/pg-parallel.mts) printed `DeprecationWarning: Calling client.query() when the client is already executing a query is deprecated and will be removed in pg@9.0` from `PgTransaction.performIO` in @prisma/adapter-pg. The same warning appears in 10 vitest workers in gates/test.log.
- **Impact:** No speed gain today, because one connection serializes the queries anyway. Once pg@9 (or an adapter that follows it) is installed, placeOrder and other transactional callers will throw.
- **Fix:** When `client` is a transaction, run the four reads one after another, or read them before opening the transaction (only placement needs them fresh). Turn the warning into a test failure (`process.on('warning')`) so it cannot come back.

#### ORD-12 ASAP copy contradicts itself: 'Ready in about 5 min, around 2:30 PM' at 2:14 PM

- **low** inconsistency, effort S, confidence 85%
- **Where:** `src/app/(site)/checkout/page.tsx:139`, `src/modules/cafe/internal/ordering-day.ts:59`, `src/modules/ordering/internal/bar.ts:97`
- **Evidence:** Live checkout at about 2:14 PM showed the ASAP label "Ready in about 5 min, around 2:30 PM" (shots.mjs output; checkout-375.png). Prep Time is 5, now + 5 = 2:19, so the first window starting at or after that is 2:30. The Bar Screen still treats every ASAP Order as makeNext, so the drink is made right away. The status page and email say "as soon as possible, around 2:30 PM".
- **Impact:** The promise ADR 0007 calls 'the product' (an honest ready time) is muddled. Customers either come at 2:30 to a drink that has been waiting 10 minutes, or are confused by two different times.
- **Fix:** Show one time. Either 'Ready around 2:19 PM (about 5 min)' with the Order's Capacity booked in the window that contains now + Prep Time (the current window when it has room), or drop the minutes and show only the window.

#### ORD-13 Stale Pay at Pickup Orders are never closed; a Reward's 9 Stars can stay reserved forever

- **low** gap, effort M, confidence 70%
- **Where:** `src/modules/ordering/internal/bar.ts:16`, `src/modules/ordering/internal/bar.ts:67`, `src/app/api/cron/daily/route.ts:18`, `src/app/(site)/orders/[id]/page.tsx:59`
- **Evidence:** expireUnpaid handles only `paymentMethod: { not: "pay_at_pickup" }`. The Bar Screen shows only today's serviceDay. The daily cron only expires online Orders and revalidates the menu. A Pay at Pickup Order never accepted (placed), or never collected (accepted to ready), stays open indefinitely: its status page keeps saying "The bar will accept it soon.", it stays cancellable, and a Reward Order keeps its `reserve` entry with no release.
- **Impact:** No-show Members lose 9 Stars until a Manager notices. Old Orders drop off the Bar Screen yet stay 'live', and reports and day views gather unresolved Orders. docs/03 section 7 defers only 'not collected' for Ready Orders.
- **Fix:** In the daily cron, close the previous days' placed Pay at Pickup Orders through transition() (cancelled by the system with the reason 'Not accepted before closing', or a new 'not_collected' status by ADR), which releases the Stars. List leftover Ready Orders for the Manager.

#### ORD-14 Guest Pay at Pickup lets one client hold a day's Capacity (no expiry, limits per IP only)

- **low** security, effort M, confidence 60%
- **Where:** `src/app/(site)/checkout/actions.ts:79`, `src/modules/ordering/internal/place.ts:207`, `src/lib/rate-limit.ts:41`
- **Evidence:** A Guest may Pay at Pickup for up to 4 drinks per Order, and these Orders never expire. Checkout allows 10 tries per Cart token (a new cookie resets it) and 20 per IP per 15 minutes, so one IP can book about 80 drinks per 15 minutes. With 12 drinks x 56 windows (672 a day), a few IPs fill every window in minutes. clientIp trusts the first X-Forwarded-For value, which is fine on Vercel only.
- **Impact:** A cheap denial of service on online ordering, which a Manager can only answer by pausing ordering or cancelling Orders one by one. Shared carrier CGNAT IPs also mean the per-IP limit can block real Customers during a rush.
- **Fix:** Cap the drinks per window held by unaccepted Guest Pay at Pickup Orders (for example at most half of Capacity). Require contact verification for Guest Pay at Pickup, or let these Orders lapse if the bar has not accepted them within X minutes after their window. Give Managers a bulk 'cancel by contact' action. Document the trusted-proxy assumption.

#### ORD-15 Lock-order inversion between a Reward placement and a cancel of the same Member's Reward Order can deadlock

- **low** bug, effort S, confidence 45%
- **Where:** `src/modules/loyalty/internal/ledger.ts:37`, `src/modules/ordering/internal/place.ts:216`, `src/modules/ordering/internal/place.ts:246`, `src/modules/ordering/internal/status.ts:153`
- **Evidence:** placeOrder takes `SELECT id FROM users ... FOR UPDATE` (canRedeem) and then the window row FOR UPDATE. A cancel or expire transition locks the order, updates the same window row (releaseWindow) and then inserts a star_entries `release` row, whose FK needs FOR KEY SHARE on the users row and so conflicts with FOR UPDATE. If the same Member places a Reward Order in window W while an earlier Reward Order of theirs in W is cancelled or expired, each waits on the other. Postgres aborts one with a deadlock error, which neither caller handles (it surfaces as a 500). Found by code review, not reproduced.
- **Impact:** Rare, but placement or expiry fails with an unhandled error (expireUnpaid runs inside Customer page renders).
- **Fix:** Use `FOR NO KEY UPDATE` for lockMember, which does not conflict with FK KEY SHARE. Or take locks in one order (window before Member) in both paths. Retry placeOrder once on 40P01/40001.

#### ORD-16 Refund after pickup keeps the redeemed Stars, contrary to docs/03 section 6

- **low** inconsistency, effort S, confidence 80%
- **Where:** `src/modules/ordering/internal/status.ts:153`, `src/modules/ordering/internal/status.ts:168`, `docs/03-ARCHITECTURE.md:91`, `docs/adr/0008-stars-ledger.md`
- **Evidence:** docs/03 section 6: "Expired, cancelled and refunded Orders give back their Pickup Window counts and reserved Stars in the same transaction as their transition." The code releases the redemption only on cancelled and expired (status.ts:153-156). For refunded-after-picked_up it only reverses earned Stars (status.ts:168-170). The section 7 table and ADR 0008 treat the Redemption as final at Picked Up.
- **Impact:** A fully refunded Reward Order costs the Member 9 Stars and gives no drink. The docs say opposite things, so either behaviour could be 'fixed' wrongly.
- **Fix:** Decide: if a full Refund should restore the Reward, call releaseRedemption on refunded-from-picked_up. Otherwise correct section 6 to say Stars return only on Cancel or Expire.

#### ORD-17 Docs disagree on the last Pickup Window and on transition() throwing

#### ORD-18 Checkout summary total ignores the Reward; only the button shows the discounted total

#### ORD-19 Status polling never expires unpaid Orders, so 'Finish paying' can outlive the 15-minute rule

- **low** gap, effort S, confidence 60%
- **Where:** `src/modules/ordering/internal/customer.ts:30`, `src/app/api/orders/[id]/status/route.ts:1`, `src/app/(site)/orders/[id]/page.tsx:111`
- **Evidence:** orderVersion() reads only status and updatedAt and does not call expireUnpaid. The full page render does. A Customer who keeps the status page open sees no version change after 15 minutes unless something else (checkout, the Bar Screen) runs the sweep, and can still pay through 'Finish paying' (PAY-04).
- **Impact:** PAY-04 timing depends on unrelated traffic, and Capacity for that window stays held.

#### ORD-20 Shortening a day with Special Hours ignores Orders already scheduled after the new closing

- **low** gap, effort M, confidence 60%

#### ORD-21 Guest Carts are never purged and leftover hk_cart cookies cost a transaction per request

- **low** inefficiency, effort S, confidence 80%
- **Where:** `src/modules/cart/internal/session.ts:27`, `src/app/api/cron/daily/route.ts:18`
- **Evidence:** Nothing deletes carts with guest_token_hash (only deleteMemberCart exists). The cron only expires Orders. After a merge, the hk_cart cookie stays for 30 days, so every render for that signed-in Member runs mergeGuestCart (BEGIN, SELECT, COMMIT), twice per page with the header button. Guest cart notes (free text) also stay forever.
- **Impact:** Unbounded table growth, extra database round trips on every page for those Members, and free-text data kept longer than the privacy notice needs.
- **Fix:** In the daily cron, delete Guest Carts not updated in 30 days. Clear the cookie after a merge (in a Server Action or the sign-in callback). Dedupe currentCartOwner per request with cache().

## Payments, webhooks, expiry and refunds

The payments core is mostly sound. The webhook route reads the raw body with request.text() and verifies it before parsing. The HMAC input for PayMongo is `t.rawBody`, compared against `te` only, which is correct with test keys. The comparison is timing-safe (sign.ts). Dedupe runs on a DB unique (provider, provider_event_id) inside the same transaction as the Order transition. The return URL never decides payment state, sk_live_ keys are refused, /dev/pay returns 404 under PayMongo, and fakePayAction throws unless the fake provider is active. Live probes on :3300 got 401 bad_signature for unsigned or tampered fake events, 404 wrong_provider for /api/webhooks/paymongo and /other, and 401 from /api/cron/daily without the secret.

The serious gap is how payments arriving at the wrong moment are handled. recordPaymentEvent only acts on a Payment that is still `pending`. Some sequences leave a Payment in another state when its money arrives: the Order expires, the Customer cancels, a payment attempt fails and the Customer retries, or the expire call to PayMongo is refused because a payment is in progress. In all of these the paid webhook is stored and then silently ignored. The Customer is charged, the Order stays Expired, Cancelled or Placed, and no code path refunds it. I reproduced this live with the fake provider: after a failed attempt, a second tab paid, and the paid event was stored but the Order stayed placed with the Payment marked failed.

Other findings:
- Payment rows are updated read-then-write with no status guard. Three concurrent Pay clicks overwrote providerPaymentId and logged a false "paid after the Order closed". Reproduced live.
- PayMongo payment.failed events can never match, because their resource is a `pay_` id, not a `cs_` id.
- A checkout that fails to start loses the Cart and holds the Pickup Window and any reserved Stars.
- Refunds are not atomic with the Order transition, and the claim is reverted on errors whose outcome is unknown.
- Refund failures are invisible to Customers and Managers.
- Smaller items: no amount, currency, reference or livemode check on paid events; no timestamp tolerance; billing details (PII) kept in payment_events; the fake-provider guard checks the configured address rather than the domain actually serving the page.

#### PAY-01 Paid webhooks for a Payment that is no longer pending are silently dropped: Customer charged, Order stays Expired/Cancelled/Placed, no refund path

- **high** bug, effort M, confidence 85%
- **Where:** `src/modules/payments/internal/payments.ts:92-99`, `src/modules/payments/internal/payments.ts:128-140`, `src/modules/ordering/internal/webhook.ts:46-53`, `src/modules/ordering/internal/refund.ts:27-30`, `tests/db/payments.test.ts:185-193`
- **Evidence:** recordPaymentEvent only looks up `status: "pending"` Payments: `if (!payment) return { kind: "ignored" };`. closeCheckout first sets the Payment to `expired` and then calls the provider. A provider error is only logged: `console.error("[payments] checkout not expired at the provider:", error)`. PayMongo docs say a checkout session 'does not expire on its own', and the expire endpoint returns 400 when the session 'has ongoing payment'. So a Customer who is mid-GCash at the 15-minute sweep, or who cancels while paying, can still complete payment. That webhook then returns `ignored`. The same happens after a `failed` event: the Payment is marked failed, and a retry in the still-active session is dropped. Live repro with the fake provider (Order K-003): I opened the checkout in two tabs, clicked Fail in tab A, then Pay in tab B. payment_events holds both events (`failed`, then `paid`), but the Order stays `placed`, the Payment stays `failed`, and provider_payment_id is empty. The paid_late branch in webhook.ts only fires in a narrow race. Its comment says a late payment 'is logged for a Manager to refund by hand', but refundOrder accepts only `picked_up` Orders, or `cancelled` Orders w
- **Impact:** Money integrity: a Customer can be charged for an Order the cafe treats as let go. Nothing tells a Manager, and no in-app refund is possible. Reachable without an attacker: a payment in flight at the 15-minute mark, a cancel during payment, a refused or failed expire call, or a retry after a failed attempt.
- **Fix:** In recordPaymentEvent, handle a paid event for any matching Payment not already paid or refunded: set status paid and providerPaymentId, and return the orderId. If transition(paid) is refused because the Order is closed, refund automatically through the provider in the same flow (or queue it), record a Refund row, and surface it in /manage/orders. Do not mark a Payment `failed` on one failed attempt while the session is still active. In closeCheckout, set `expired` only after the provider confirms, or keep it pending when the provider refuses. Replace the 'ignored after expiry' test with 'refunded after expiry'. Build it test-first per CLAUDE.md.
- **Refs:** ADR 0003; PRD PAY-03, PAY-04, PAY-05; docs/04-DATA-MODEL.md invariant 3; https://docs.paymongo.com/reference/checkout-session-resource.md; https://docs.paymongo.com/reference/create_checkout_sessions_id_expire.md

#### PAY-02 Payment rows are updated read-then-write with no status guard: closeCheckout can overwrite paid with expired, and concurrent paid events clobber providerPaymentId

- **medium** bug, effort S, confidence 85%
- **Where:** `src/modules/payments/internal/payments.ts:92-111`, `src/modules/payments/internal/payments.ts:129-134`
- **Evidence:** recordPaymentEvent reads with findFirst `status: "pending"` (no lock), then calls `tx.payment.update({ where: { id: payment.id }, data: { status: "paid", providerPaymentId: event.paymentId } })`. closeCheckout reads the Payment, then calls `db.payment.update({ where: { id: payment.id }, data: { status: "expired" } })`. Neither write has a status condition. Live repro (Order K-004): three tabs clicked Pay on the same /dev/pay page at once. The Order went placed→paid once. The Payment ended with provider_payment_id `fake_pay_b4b0...` from the 2nd event, not `fake_pay_1df8...`, which paid the Order. server.log printed `[payments] paid after the Order closed: 8c77c674-...` for an Order that was not closed. The same pattern lets this interleaving overwrite paid with expired: closeCheckout reads pending; the webhook updates to paid, gets paid_late, and commits; closeCheckout's blocked update then writes `expired`.
- **Impact:** The audit trail of a captured payment can be lost: Payment shows expired although money was taken. Refunds could target the wrong provider payment id. False 'paid after the Order closed' alarms appear.
- **Fix:** Use guarded updates: `updateMany({ where: { id, status: "pending" }, data: ... })` and act only when count === 1. Or lock the payment row (`SELECT ... FOR UPDATE`) before deciding. Make closeCheckout's write conditional on `status: "pending"` as well.
- **Refs:** ADR 0003

#### PAY-03 When the checkout fails to start, the Cart is already emptied and the Order keeps holding the Pickup Window and reserved Stars

- **medium** bug, effort M, confidence 90%
- **Where:** `src/modules/ordering/internal/place.ts:301-302`, `src/modules/ordering/internal/place.ts:320-333`, `src/app/(site)/checkout/actions.ts:54-55`
- **Evidence:** placeOrder commits the Order and runs `await clearCart(input.owner, tx);` inside the transaction. Only after commit does it call startPayment. On error it returns `{ ok: false, reason: "payment_start_failed" }` with no orderId. Its comment reads 'The Order stays Placed and Expires in 15 minutes, freeing its window'. The Customer is told "We couldn't open the payment page. Try again, or choose Pay at Pickup." Their Cart is empty, so they cannot try again, and they have no link to the Placed Order. Its window counts and any 9 reserved Stars stay held until a sweep expires it.
- **Impact:** Any PayMongo outage or timeout loses the Customer's Cart. It also blocks Capacity and the Member's Reward for 15+ minutes, and leaves an orphan Placed Order on the day view.
- **Fix:** On startPayment failure, close the Order straight away through transition(expired or cancelled, system), which releases the window and Stars in the same transaction. Then restore the Cart from the snapshot Lines, or create the checkout before clearing the Cart. Add a DB test with a provider whose createCheckout throws.
- **Refs:** ADR 0007; ADR 0008; PRD PAY-01, PAY-04

#### PAY-04 Refunds are not atomic with the Order transition, and the claim is reverted on errors whose outcome is unknown; both can leave Orders stuck

- **medium** bug, effort M, confidence 75%
- **Where:** `src/modules/payments/internal/payments.ts:150-187`, `src/modules/ordering/internal/refund.ts:32-49`, `prisma/schema.prisma:407-419`
- **Evidence:** refundPayment claims paid→refunded, calls the provider, then creates the Refund row. Any throw, including a network timeout after PayMongo processed the refund or a failed `db.refund.create`, runs `status: "paid"`. A retry then asks the provider to refund again: PayMongo refuses, so the Order stays refundable forever while money was in fact returned. refundOrder runs transition(refunded) as a separate step after refundPayment. A crash or a refused transition leaves the Payment `refunded` with the Order still `picked_up`/`cancelled`. Every retry then gets `already_refunded` → `{ ok: false, reason: "not_allowed" }`, so the Order can never reach Refunded and Stars are never reversed. PayMongo refunds are asynchronous (pending → succeeded/failed), but refund events map to `other` and are ignored, so a refund that later fails is never seen. refunds.payment_id has no unique index, although refunds are full only. Separately, a Payment that exists in a non-paid state returns `no_online_payment`, which refundOrder treats like cash: it marks the Order Refunded and emails 'refunded in full' without moving money. That case is latent today.
- **Impact:** Refund state can drift from the provider and Orders can get stuck. Refund failures at the provider go unnoticed.
- **Fix:** Keep the claim when the outcome is unknown, and reconcile through the provider's refund webhooks (payment.refunded, payment.refund.updated). Let refundOrder continue to transition when refundPayment returns already_refunded and the Order is not yet Refunded, so the operation is idempotent end to end. Add a unique index on refunds.payment_id. Return a distinct outcome for an online Payment that is not paid.
- **Refs:** PRD PAY-05; ADR 0003

#### PAY-05 Refund failures are invisible: refundAction and cancelOrder throw away the RefundResult

- **medium** gap, effort S, confidence 85%
- **Where:** `src/app/manage/orders/actions.ts:14-17`, `src/modules/ordering/internal/refund.ts:62-71`, `src/app/(site)/orders/[id]/actions.ts:8-14`
- **Evidence:** refundAction calls `await refundOrder(...)` and then `refresh()` without reading `{ ok: false, reason: "provider_failed" }`. cancelOrder calls `await refundOrder(orderId, ...)` for a paid Order and returns only the cancel's TransitionResult. When the provider refuses, a Customer who cancels a paid Order sees 'This order was cancelled.' and gets no refund email. The only trace is `console.error("[payments] refund refused by the provider:", error)`. The Manager sees the same Refund button again with no message.
- **Impact:** A Customer's money may never come back after a cancel, and nobody is told. A Manager pressing Refund cannot tell success from failure.
- **Fix:** Return the RefundResult to the Server Actions and show a message ('The refund didn't go through. Try again in a minute.'). Flag cancelled-but-paid Orders that have no Refund row on /manage/orders. Have the Customer page say the refund is pending, not finished.
- **Refs:** PRD PAY-05, ORD-09

#### PAY-06 PayMongo payment.failed events can never match a Payment (the resource id is pay_, not the checkout session id)

- **low** bug, effort S, confidence 80%
- **Where:** `src/modules/payments/internal/paymongo.ts:101-113`

#### PAY-07 A webhook can mark an Order Paid long after its 15 minutes when no expiry sweep has run

- **low** bug, effort S, confidence 70%

#### PAY-08 Paid events are not checked for amount, currency, reference number or livemode

#### PAY-09 PayMongo signature check has no timestamp tolerance, and the whole unauthenticated body is read before verification

## Identity, sign-in and access control

### Pass 1

Access control holds. I checked every page and Server Action under /manage and /bar, and every route handler in scope, by reading the code and by sending real requests to http://localhost:3300 as signed out, as a Member, as the Barista and as the Manager without a Second Factor. Each one re-checks the role on the server. A Member gets 404 from every Staff action and from /api/bar. A Barista gets 404 from Manager-only actions (refund, cancel, Adjust Stars, Inquiries, Cancel at the bar). A Manager without the Second Factor is sent to /manage/two-factor from every /manage action, including cancelAtBar. /bar and /api/bar skip the Second Factor, as ADR 0005 and 0014 intend. Better Auth refuses foreign or missing Origin headers on POST (403), and Next refuses a Server Action from a foreign Origin. Sign-in links are about 190-bit tokens that work once and expire after 5 minutes; a used link gives INVALID_TOKEN, and a foreign callbackURL gives 403. The sign-in form answers the same for every address, so it does not reveal who has an account. Favourites, Order again and the data export are all scoped to the signed-in Member, so I found no IDOR. Order links use a 256-bit HMAC token; only its hash is stored, and a wrong or missing token gets 404.

The real problems sit around the edges. (1) Deleting an account does not remove pending sign-in links. The code deletes `verifications` rows by email, but Better Auth stores them as `magic-link:<token>`. A link sent before the deletion still signs in afterwards and creates a fresh account with the same email; I confirmed this live. (2) The per-email link limit lets anyone lock a chosen person, such as the Manager, out of sign-in, and flood their inbox with up to 288 links a day. (3) Better Auth's own HTTP endpoints stay open even though the app never calls them. /api/auth/update-user skips the app's 60-character name limit (a 200,000-character name was stored), and /api/auth/get-session and /list-sessions hand session tokens to JavaScript. (4) The 5-minute session cookie cache keeps a revoked session working; a stolen cookie copy still exported data and deleted the account after revoke-sessions. (5) Per-IP limits trust X-Forwarded-For, which a client can set on any host except Vercel. (6) The Second Factor check depends on a redirect-path string, which already caused one bug (batch 5.3). (7) There is no Staff management at all, although ADR 0005 and section 13 promise a Manager invite. (8) The data export and account deletion miss data stored by email: guest Orders, Event sign-ups and Inquiries; the export also leaves out Favourites. Smaller points: an expired link lands on sign-in with no message, one secret serves three jobs, Order Status changes are audited outside audit_log, and better-auth is behind 1.7.16.

I removed every test account I made and signed out the Staff sessions I opened. I did not create two_factors rows for the seeded Staff, and I toggled no shared settings.

#### ID1-01 Account deletion leaves pending sign-in links working; they sign in to a new account with the deleted email

#### ID1-02 Per-email sign-in limit lets anyone lock a chosen person (such as the Manager) out of sign-in and flood their inbox

- **medium** security, effort S, confidence 90%
- **Where:** `src/app/(site)/sign-in/actions.ts:33-42`, `src/lib/rate-limit.ts:9-24`
- **Evidence:** The limit is `takeToken(`link:${email}`, 3, FIFTEEN_MINUTES)`, keyed only on the target address. ## Web security: headers, CSP, input handling, uploads, cron, dependencies

### Pass 1

The web security surface is mostly solid. The CSP and headers match ADR 0013. Next rejected a cross-origin Server Action (500, "Invalid Server Actions request"). Open redirects are closed in safeNext and in Better Auth's callbackURL check (403 on 10 bypass variants). Markdown renders safely (skipHtml plus react-markdown's URL filter), and JSON-LD escapes "<". Magic links work once only and cookies are HttpOnly with SameSite=Lax. No CORS headers are sent, and Better Auth's password sign-up, change-email and HTTP magic-link routes are closed. Cron fails closed, webhook signatures are compared in constant time, there is no unsafe raw SQL, and reflected form values were escaped in a live test.

The serious problems are file writes built from user input:
- **Event Sign-up email (high).** The Sign-up form validates email with a loose regex, and the dev/self-host mail outbox uses that address as a file name. An unauthenticated visitor can write a .txt file anywhere on disk whenever Resend is off and the app is not on Vercel. That is the case on the server running now, and `next dev` and `next start` listen on all network interfaces.
- **Menu photo upload (medium).** The photo is saved under the raw form slug before the slug is validated.

Live probes found these weaker spots:
- Better Auth's `/api/auth/update-user` skips the app's profile validation. It accepted a 1 MB name and an `image` of `javascript:alert(1)`, and `/list-sessions` returns raw session tokens.
- Per-IP rate limits trust the first X-Forwarded-For value, so spoofing it gets around them anywhere but Vercel.
- The webhook route reads bodies of any size before checking the signature (a 30 MB body was accepted).
- A NUL byte in any public text field causes a Postgres 22021 error and a 500. There is no error.tsx, so the browser shows Next's unbranded "This page couldn't load" page, without the Concept Notice, and the typed form is lost.

Operational and logic risks:
- vercel.json runs `prisma migrate deploy` on every build, and the setup doc gives Preview the production database.
- A payment that arrives after its Order expired is answered "ignored" with no log, although the code comment promises one.
- Event Sign-ups are unverified and have no bot protection.
- better-auth 1.7.10 is older than the 1.7.16 security release of 2026-11-03.

#### SEC1-01 Unauthenticated arbitrary file write: an Event Sign-up email becomes a file path in the mail outbox

- **high** security, effort S, confidence 85%
- **Where:** `src/modules/notify/internal/outbox.ts:60`, `src/modules/content/internal/signups.ts:9-17`, `src/app/(site)/events/[slug]/actions.ts:58`
- **Evidence:** The Sign-up schema checks email only with `.regex(/^[^\s@]+@[^\s@]+\.[^\s@]+$/)`, which accepts '/' and '..'. Checkout uses z.email() and Better Auth uses z.email(), both of which reject it. send() then runs `path.join(dir, `${stamp}-${randomBytes(3).toString("hex")}-${email.to}.txt`)` whenever RESEND_API_KEY is empty and VERCEL is unset. A node simulation with the real zod schema gave: `signup regex accepts: true | z.email() accepts: false`. The address "x@../../../../../../../appdata/local/temp/pwn.txt" resolves to `C:\Users\cjose\Documents\appdata\local\temp\pwn.txt.txt`. The fake first segment ('<stamp>-x@..') absorbs one '..'. The server on :3300 runs with these settings (it writes data/mail). This was not exploited live, to avoid taking a Seat on a seeded Event.
- **Impact:** On dev machines (`next dev` listens on all interfaces), CI/e2e, or any self-hosted `next start` without Resend, an anonymous visitor can create or overwrite any *.txt file the process can write. Examples: public/robots.txt or ads.txt, which `next start` serves at once. Part of the content is attacker text (name, 80 chars). A Sign-up row is also created. Vercel with Resend is not affected.
- **Fix:** Use z.email() in signups.ts and inquiries.ts, as checkout does. In outbox.ts, build the file name from a sanitised value only, for example `email.to.replace(/[^a-z0-9@._-]/gi, "_")`. Then check that `path.resolve(file).startsWith(dir + path.sep)`. Add one unit test with a '../' address.

#### SEC2-01 Event Sign-up email becomes a file path in the email outbox: anyone can write .txt files anywhere on the server

- **high** security, effort S, confidence 90%
- **Where:** `src/modules/notify/internal/outbox.ts:53-61`, `src/modules/content/internal/signups.ts:9-17`, `src/app/(site)/events/[slug]/actions.ts:59`, `src/modules/content/internal/inquiries.ts:23-31`
- **Evidence:** outbox.ts:60 builds the file name from the raw recipient: path.join(dir, `${stamp}-${randomBytes(3).toString("hex")}-${email.to}.txt`). The Sign-up schema only checks .regex(/^[^\s@]+@[^\s@]+\.[^\s@]+$/), which accepts '/', '\\' and '..', and the action sends to result.signup.email. Orders use z.email() and sign-in uses Better Auth's z.email(), so those paths are safe. Reproduced with the real send() (tsx, scratchpad/audit/websec/outbox-demo/demo.mts, no RESEND_API_KEY, no VERCEL): to='x@a.b/../../../public/robots' passes the Sign-up regex, and the file is written to <cwd>/public/robots.txt rather than data/mail. Its content starts 'To: x@a.b/../../../public/robots\nSubject: You're in'. With the server's cwd at the repo, 'x@a.b/../../../src/app/pwned' resolves to <repo>/src/app/pwned.txt (scratchpad/audit/websec/traversal.mjs). The server listens on all interfaces ('Network: http://172.31.240.1:3300' in server.log). Not run live, so no seeded Event seat was taken.
- **Impact:** The setup is the documented local default and also any self-host without Resend: an unauthenticated visitor (or anyone on the LAN of a dev machine) can create or overwrite any *.txt file the Node process can write. Each Sign-up writes one file, with partly attacker-chosen content (name up to 80 characters), at up to 10 per hour per IP. Other effects: filling the disk, planting files under public/ or src/, and corrupting data/mail, which the e2e tests read. Add one outbox test with a traversal address.

#### PERF-01 Signing in with a guest Cart crashes the first /checkout or /cart render (concurrent guest Cart merges)

#### PERF-02 Bar Screen poll version ignores makeNext and Prep Time, so Scheduled Orders stay under "Later today"

- **high** bug, effort S, confidence 88%
- **Where:** `src/modules/ordering/internal/bar.ts:85`, `src/modules/ordering/internal/bar.ts:96-98`, `src/app/api/bar/route.ts:16`, `src/app/bar/bar-screen.tsx:106-107`
- **Evidence:** The version is `${rows.length}:${latest}:${paused?.until.getTime() ?? 0}` (bar.ts:85). Each Order's `makeNext` depends on the clock and Prep Time: `order.pickupKind === "asap" || order.windowStart.getTime() - prep * 60_000 <= at.getTime()` (bar.ts:96-98). The route answers `{ same: true }` when the version matches (route.ts:16), and the client returns early on `if ("same" in data) return;` (bar-screen.tsx:107). As time passes, an Order's makeNext flips, but no row changes, so the version stays the same and the client never gets the new board. A Manager changing Prep Time in /manage/hours does not change the version either.

- **Fix:** Put the time-dependent part into the version, for example `${rows.length}:${latest}:${paused}:${prep}:${makeNextCount}`. Or send `prepMinutes` and let the client compute makeNext from windowStart on each tick. Add a vitest case for barBoard: with a frozen clock moved past windowStart minus prep, the version must change.
- **Refs:** ADR 0009; docs/05-DESIGN-SYSTEM.md section 9; STAFF-02

#### PERF-03 Signed-out Bar Screen poll follows a redirect to the sign-in HTML (55.6 kB), JSON parsing throws and the board freezes silently
