### CK-01 Anyone can create guest Carts without limit (P2)

**What:** adding to the Cart has no rate limit, and a Cart has no cap on how many lines it holds. Each request without the Cart cookie makes a new guest Cart, which lives for 30 days.

**Why it matters:** a script could fill the free database (0.5 GB) with junk Carts and Cart lines. The database would then stop, and every page that reads data would fail. Checkout, sign-in, Inquiries and Event Sign-ups already have limits; the Cart does not.

**Fix:**

1. Add `limits.addToCart(ip)` in `src/lib/limits.ts`, for example 60 adds per 15 minutes per IP, used by `addToCartAction` and `changeLineAction`.
2. Cap a Cart at 30 lines in `addLine`, with the message "Your cart is full. Check out or remove something first."
3. Tests in `tests/db/limits.test.ts` and the cart tests.

### CK-02 The pages miss the "blocking time under 200 ms" budget (P2)

**What:** the design system's budget is Performance 90 or more, LCP under 2.5 s, CLS under 0.05 and total blocking time under 200 ms. Lighthouse (mobile) on the live site measured:

| Page | Performance | LCP | Total blocking time | CLS |
| --- | --- | --- | --- | --- |
| Home | 94 | 1.9 s | 260 ms | 0 |
| `/menu` | 94 | 2.4 s | 220 ms | 0 |
| A Menu Item (`/menu/item/hoshi-latte`) | 84, then 90 and 89 | 2.5 to 2.6 s | 330 to 500 ms | 0.003 |

Accessibility and Best Practices are 100 on all three.

**Why it matters:** blocking time is how long the page is too busy to answer a tap. The Menu Item page is where people choose their drink, and it is the slowest.

**Where it stands (13.2):** the money formatter and the header height were fixed; Home and `/menu` meet the budget, and the Menu Item page went from 388 to 234 ms locally. Even with no Option Picker at all that page measures about 203 ms, so the rest is the framework's own start-up, and it is left as it is.

**Fix, as first written:** profile the Menu Item page in a production build. Most of the time is spent in the framework's main script while the page becomes interactive. Look at what loads in the browser there (the Option Picker and its icons), and load later anything not needed for the first tap. Then measure again on the live site, three runs each.

### CK-03 A small photo file can unpack into a huge image (P3)

**What:** uploads are capped at 2 MB, but `sharp`, the image tool, unpacks up to 268 million pixels by default. A 2 MB PNG of a plain colour can be 16,000 by 16,000 pixels, about 1 GB of memory once unpacked.

**Why it matters:** one such upload could stall or crash the save. Only Managers, signed in with their Second Factor, can upload, so the risk is low.

**Fix:** in `src/lib/photo.ts`, give `sharp` a `limitInputPixels` of about 40 million, and shrink every photo to at most 2,400 pixels on its long side. That also makes stored photos smaller.

### CK-04 A photo can be replaced but never removed (P3)

**What:** Menu Items, Events and Posts take a photo, and a new file replaces it. There is no way to go back to no photo.

**Fix:** a **Remove photo** checkbox under the saved photo. Saving with it ticked clears the photo and deletes the file, as replacing does.

### CK-05 There is no `robots.txt` (P3)

**What:** `/robots.txt` and `/sitemap.xml` return the "Page not found" page. Every page already says `noindex`, so search engines leave the site out, as decided (the address is invented). Lighthouse's only SEO fail is that one, and it is on purpose.

**Fix:** add `src/app/robots.ts` that lets crawlers in (`Allow: /`), so the file exists and answers properly. It must not block them: a crawler has to fetch a page to read its `noindex`, and a blocked address that is linked elsewhere can still show in search, without its page. (This report first said `Disallow: /`; that was wrong, and `layout.tsx` already explains why.)

### CK-06 The site's description still names Kapitolyo, Pasig (P3)

**What:** since batch 12.9 the docs call Hoshikopi just "a concept cafe". The site's own description, which search results and link previews show, still reads "A concept cafe in Kapitolyo, Pasig. Order ahead for pickup and earn Stars."

**Fix:** the owner decides. If the site should match the docs, change the description to "A concept cafe. Order ahead for pickup and earn Stars." The Visit page still shows its invented neighbourhood, as the PRD says.

### CK-07 A browser test leaves a photo file behind each run (P3)

**What:** the test "a Manager publishes an Event" uploads a small photo. On a computer it lands in `data/menu-photos/`, and nothing deletes it. Git ignores that folder, so it only adds clutter, about 4 kB a run.

**Fix:** delete the file at the end of the test, or empty the folder's test photos when the e2e database is reset.

### CK-08 Preview deployments use the live database (P3)

**What:** a Vercel preview, the test address each pull request gets, uses the live database and photo storage. The docs say so. It is well guarded:

- Vercel asks for the owner's login before a preview opens (checked: a stranger is sent to the Vercel sign-in);
- database migrations run only on Production builds (`vercel.json`).

Still, trying an unmerged change on its preview can change live data.

**Fix (optional):** Neon's Vercel integration can give each preview its own copy of the database, a branch, so previews never touch live data.

**Decision (owner, 2026-11-18): on hold.** The live site is itself the demo, so previews sharing its data is acceptable for now. The steps are in [docs/06-SETUP.md](../06-SETUP.md) section 9 for when that changes.

### CK-09 The picomatch exception is still needed (P3)

**What:** `scripts/audit.mjs` lets one advisory through: picomatch (GHSA-fc5q-39xc-vjpf), which reaches only the test tools. No fixed version exists yet; the latest is 4.0.7.

**Fix:** none now. When the audit prints "no longer reported: remove it", delete that line.

## 3. Checked and sound

- **Roles:** every Staff Server Action checks the role first (a test finds every action file, so a new one cannot miss it). The new Member lookup on Adjust Stars is Manager-only.
- **Customers' own data:** account actions read the signed-in Member; Cart actions read the Cart cookie; Order pages, the Order status poll and the calendar file need the Order's secret link; Sign-up links need their token.
- **Sign-in redirects:** `safeNext` accepts only paths on this site. It refuses `//`, backslashes and control characters.
- **Raw HTML:** the structured data escapes `<`. Markdown skips raw HTML. React escapes everything else, alt text included.
- **Payments:** payment state comes only from signed webhooks; the webhook route has a rate limit and a 64 kB cap; an unsigned call gets 401.
- **Uploads:** the type is read from the file's first bytes, the size is capped at 2 MB, location data is stripped, and a file is stored only after the save passes. The local photo route refuses path tricks (400).
- **Protected endpoints, asked as a stranger:** the daily job, the Bar Screen poll and the account export answer 401; a wrong Order token gets 404. Staff pages send a stranger to sign-in and show no Staff data.
- **Live security headers:** a Content Security Policy, HSTS, `X-Frame-Options: DENY`, `nosniff`, a strict referrer policy, and camera, microphone and location turned off. Inline scripts are allowed on purpose (ADR 0013).
- **Rate limits:** sign-in links, Google sign-in, checkout, Pay at Pickup, Inquiries, Event Sign-ups and webhooks. They read the visitor's address from the header Vercel overwrites, so it cannot be faked on Vercel.
- **Publishing:** a saved change now shows on its own page at the next visit (batch 12.8).
- **Every public page loads** on the live site (200, under 0.6 s); unknown addresses get 404.
